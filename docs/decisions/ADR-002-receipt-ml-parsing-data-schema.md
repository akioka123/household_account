# ADR-002: レシートML解析に備え、複数個割引は生データ構造のまま保持し案分は決定的関数に分離する

- 日付: 2026-08-27 / 状態: 検討中(フェーズ3着手時に確定)

## 背景(Why)

receipt-parse スキルによるレシート解析で、複数個割引行(例:「1コ119、3コ328」)が現れる。household_account の生活費品目データは `Money` が0以上の値しか持てない制約上、割引行を独立した負の行にはできず、値引き後の実購入額を対象品目へ案分して1品目1行の金額として記録している。

この案分値(例: 119円×3点の割引後328円を109/109/110円に分割)は、割引総額を何個の品目にどう配分するかという**人(またはLLM)の判断**で決まる。端数の寄せ方に一意の正解はなく、同じレシートでも解析者によって109/109/110にも108/110/110にもなり得る。

フェーズ3(US-07)でレシート画像からのML/OCR自動抽出を行う場合、フェーズ2で保存した「画像+人手解析結果」のペアを教師データとして使う想定である(`docs/03-basic-design.md` 5章)。しかし教師ラベルが案分後の金額(人による判断が混入した値)だと、モデルは「レシートに印字された内容」ではなく「解析者の案分の癖」を学習することになり、ラベルの一貫性が保証されないため学習データとして不適切である。

## 決定(What)

フェーズ3のデータ設計では、教師データのラベルを **レシートに印字された生の構造**(品目名・単価・個数・割引グループとその合計額)で保持し、案分(グループ割引額を各品目へ配分し1品目1行の非負金額にする処理)は独立した決定的関数として、ラベル生成時・推論時の両方で同一ロジックを適用する。

- 案分アルゴリズム自体はテスト可能な純粋関数として実装し、フェーズ2(人手解析)・フェーズ3(ML推論後の後処理)の両方から呼び出す共通ロジックとする
- MLモデルが解くタスクは「印字された品目・単価・個数・割引グループを読み取る」構造化抽出に限定し、案分の判断はモデルに学習させない

## 実施方法(How)

本ADRは方針の記録であり、具体的な実装(教師データのスキーマ、案分関数の配置場所等)はフェーズ3のゲート1〜4で設計する。着手時に本ADRを参照し、以下を検討すること:

- 教師データのスキーマに割引グループ(対象品目群・グループ合計額・グループ内個数)を表現するフィールドを追加する
- フェーズ2の「貼り付けで一括登録」TSV形式(品目名/金額/小分類のフラット3列)は現状維持してよいか、教師データ保存用に別途リッチな形式(画像に紐づくJSON等)を追加するかを判断する
- 案分関数の端数処理ルール(どの品目に余りを寄せるか)を明文化し、フェーズ2・3で同一ルールを使う

## 採らなかった選択肢と理由(Why not)

- **案分後の金額をそのまま教師データのラベルとする(現状のフェーズ2出力をそのまま流用)**: 解析者ごとに端数の寄せ方が変わり得るため、同一レシートでもラベルが安定せず、モデルが再現性のない基準を学習することになるため採らない。
- **割引行を非負制約に反しても独立行として保持する**: `Money` の不変条件(減算結果が負になると例外)を回避するために品目データの制約自体を緩めることになり、家計簿ドメインの他の計算(損益等)に影響する範囲が広がるため採らない。

## しないこと(スコープ除外)

- 本ADRの時点でML/OCR自動抽出の実装(US-07)には着手しない。US-07は現行フェーズでは対象外(Won't)であり、本ADRは将来の再検討時の前提を記録するのみ。
- フェーズ2の「貼り付けで一括登録」TSV形式・`receipt_paste_parser.py` の仕様変更は本ADR単独では行わない。

## 再検討条件

フェーズ3(US-07、OCR/ML自動抽出)の企画・設計に着手する際、本ADRの方針を前提として教師データスキーマと案分関数の設計を確定し、状態を「承認済」に更新する。
