# ユーザーストーリー: レシート金額抽出・生活費入力の詳細化

- 日付: 2026-08-24
- 対象範囲: 本機能（レシート金額抽出・生活費入力の詳細化）専用。既存アプリ全体のストーリーは対象外
- 参照元: `docs/proposal/receipt-amount-extraction.md`（企画書）、`docs/00-requirements-notes.md`（要件確認ノート）

## ペルソナ定義

| ペルソナ | 説明 |
|---|---|
| 利用者(本人) | 本アプリを個人・ローカルで運用し、買い物のたびにレシートを持ち帰って生活費を記録し、月次で家計を見直す唯一の利用者。PCから操作する。週3回以上の頻度で利用する。 |

## ストーリー一覧

## US-01: レシート画像のアップロード・保存 [Must]
利用者(本人)として、買い物で受け取ったレシートの画像をアプリに保存したい。なぜなら、レシート原本は保管せず、画像がアプリ外でClaudeに読ませて品目データ化する際の唯一の参照元になるから。

**受け入れ基準**(すべて検証可能な条件で書く):
- [ ] 画面から画像ファイル（レシートの写真）をアップロードできる
- [ ] アップロードした画像はファイルシステムに保存され、DBには画像ファイルへの相対パスが記録される（画像バイナリ自体はDBに保存しない）
- [ ] アップロードした画像は、アップロード操作とは別のタイミング（後日の画面表示）で参照・表示できる
- [ ] 画像は特定の対象年月（YearMonthで表現される年・月）に紐づけて保存される
- [ ] 画像として読み込めないファイルがアップロードされた場合、保存は行われず利用者にエラーが表示される

## US-02: 品目単位（品目名・金額・小分類）での生活費入力 [Must]
利用者(本人)として、レシートから得た品目ごとに品目名・金額・小分類を入力して生活費として記録したい。なぜなら、生活費を「食品」「生活用品」等の単位で見直せるようにすることが本機能の目的そのものだから。

**受け入れ基準**(すべて検証可能な条件で書く):
- [ ] 対象年月を指定し、品目名・金額・小分類を1件ずつ入力して保存できる
- [ ] 金額は0以上の整数として保存され、0未満の値を入力した場合は保存時にエラーとなる
- [ ] 品目には食品・生活用品など複数の小分類のうち1つを付けられる（少なくとも2種類以上の小分類を区別して記録できる。固定リストの内容はここでは確定しない）
- [ ] 対象年月を指定すると、その年月に保存済みの品目データ（品目名・金額・小分類）を一覧で確認できる
- [ ] 保存済みの品目データ（品目名・金額・小分類）を編集し、変更内容を保存できる
- [ ] 保存済みの品目データを削除できる
- [ ] 品目単位のデータと既存の生活費手入力（内訳なしの簡易入力）は、同じ対象年月内で共存して保存できる
- [ ] 品目単位のデータを保存・編集・削除しても、既存の生活費手入力機能（食費/電気代/ガス代/携帯料金/通信費の5カテゴリでの簡易入力）は変更後も利用可能なまま維持される

## US-03: 読み取り結果（品目一覧）の貼り付け一括登録 [Should]
利用者(本人)として、アプリ外でClaudeに読ませて得た品目一覧の読み取り結果を画面に貼り付けて一括登録したい。なぜなら、週3回以上発生する買い物のたびに品目を1件ずつ手入力する手間を省き、教師データの登録を効率化したいから。

**受け入れ基準**(すべて検証可能な条件で書く):
- [ ] 画面上の入力欄にテキストを貼り付けると、品目一覧（品目名・金額・小分類の組）として画面に表示される
- [ ] 貼り付けられた品目一覧は、保存を実行する前に画面上で内容を確認できる
- [ ] 保存を実行する前に、貼り付けられた品目一覧の各行（品目名・金額・小分類）を修正できる
- [ ] 確認・修正後に一括保存を実行すると、保存された全品目が US-02 の品目データと同じ形式・同じ保存先に登録される
- [ ] 想定した形式（品目名・金額・小分類の組）に一致しないテキストが貼り付けられた場合、保存は実行されず利用者にエラーまたは警告が表示される

## US-04: 小分類別の月次集計表示 [Must]
利用者(本人)として、対象年月の品目データを小分類ごとに合計した金額を確認したい。なぜなら、「食品」「生活用品」等の単位で生活費を見直すという本機能の目的を、月次の数値として確認できる形にする必要があるから。

**受け入れ基準**(すべて検証可能な条件で書く):
- [ ] 対象年月を指定すると、その年月に登録された品目データが小分類ごとの合計金額で表示される
- [ ] 表示される小分類ごとの合計金額は、その年月に登録された全品目の金額を小分類単位で合算した値と一致する
- [ ] 集計画面には品目名は一覧表示されない（表示されるのは小分類単位の合計金額のみ）
- [ ] 品目データが1件も登録されていない小分類の扱い（0円として表示する、または表示対象から除外する）が、全小分類で一貫している

## US-05: 既存の生活費簡易入力の廃止 [Won't]
利用者(本人)として、既存の生活費手入力（食費/電気代/ガス代/携帯料金/通信費の5カテゴリ、内訳なしの簡易入力）を廃止せずそのまま使い続けたい。なぜなら、レシートを保存しない支出や品目分解が不要な場面でも、これまでどおり記録を続けられる必要があるから。

本エントリは「既存機能を廃止しない」ことを明示するための Won't であり、共存要求そのものは US-02 の受け入れ基準に反映済み。
**理由（やらない理由）**: 新機能（品目単位入力）は追加機能であり既存機能の置き換えではない。企画書のスコープ境界および要件確認ノートで、既存の生活費手入力の廃止は明示的に対象外とされている。

## US-06: カード請求の自動読取・CSV連携 [Won't]
利用者(本人)として、カード請求明細も自動で読み取ってCSV連携してほしいと思うことがあるが、今回はレシート（現金支出）の記録に限定したい。なぜなら、カード請求の自動読取・CSV連携は別途独立した機能として検討すべきスコープであり、今回はレシート（現金支出）にスコープを絞る必要があるから。

**理由（やらない理由）**: 別途独立した機能として検討予定であり、今回はレシート（現金支出）の記録に限定してスコープを絞るため。

## US-07: フェーズ3（OCR/MLによる自動抽出） [Won't]
利用者(本人)として、レシート画像からOCR・機械学習分類器で品目・金額を自動抽出してほしいと思うことがあるが、今回（フェーズ2）は対象外としたい。なぜなら、フェーズ2（本機能）で教師データが目安100件貯まってから精度実現性を含めて改めて企画判断すべきであり、現段階で着手すると過剰投資になるから。

**理由（やらない理由）**: フェーズ2（本機能）で教師データが目安100件貯まってから、精度実現性を含めて改めて企画判断する。現段階で着手すると過剰投資になるため。

## US-08: アプリからの外部AI API呼び出し [Won't]
利用者(本人)として、アプリ本体からClaude等の外部AI APIを自動で呼び出してレシートを読み取ってほしいと思うことがあるが、今回は組み込まず、アプリ外で自分が手動でClaudeを操作し、その結果をUS-03の貼り付け機能でアプリに登録する運用にしたい。なぜなら、外部AI APIをアプリに組み込むと有料サービス契約に該当し、運用費0円の制約に反するとともに、グローバルルール上ユーザーの事前確認が必要になるから。

**理由（やらない理由）**: 運用費0円の制約を満たすため。アプリに組み込む場合は有料サービス契約に該当し、グローバルルール上ユーザーの事前確認が必要になる。

## US-09: スマホからの画像アップロード対応 [Won't]
利用者(本人)として、スマートフォンからもレシート画像をアップロードできてほしいと思うことがあるが、今回はPC画面のみに対応したい。なぜなら、利用者（本人）はPCのみで運用する前提であり、対応不要な画面幅対応（レスポンシブ対応）にコストをかける必要がないから。

**理由（やらない理由）**: 利用者（本人）はPCのみで運用する前提であり、対応不要な画面幅対応にコストをかけないため。

## US-10: 品目名の月次画面への一覧表示 [Won't]
利用者(本人)として、月次集計画面でも品目名を一覧表示してほしいと思うことがあるが、今回は小分類ごとの合計金額のみを表示したい。品目名はDB上のデータ（教師データ用の記録）としては保持するが、月次画面には表示しない。なぜなら、集計は小分類単位で十分であり、品目名の一覧表示は本機能の目的（小分類での見直し）には必須ではないから。

US-04の小分類別集計とは矛盾しない（集計対象データとしては使うが、画面表示はしないという整理）。
**理由（やらない理由）**: 集計は小分類単位で十分であり、品目名の一覧表示は本機能の目的（小分類での見直し）に必須ではないため。

## US-11: 新規の定期バックアップ強化 [Won't]
利用者(本人)として、レシート画像・品目データを対象とした新規の定期バックアップ機構を追加してほしいと思うことがあるが、今回は追加せず既存のpg_dump手動バックアップ運用のままにしたい。なぜなら、既存のpg_dump手動バックアップ運用のままで実害なしと利用者自身が判断しているから。

**理由（やらない理由）**: 既存のpg_dump手動バックアップ運用のままで実害なしと利用者が判断したため。
