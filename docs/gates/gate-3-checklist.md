# ゲート3 チェックリスト: 非機能要件（NFR）作成（レシート金額抽出・生活費入力の詳細化）

- 対象成果物: `docs/02-nfr.md`
- 対応する作業指示書: `docs/work-orders/3-nfr-order.md`
- 使用スキル: `gate-check`（判定レポートは `docs/gates/gate-3-report.md` に作成）
- 判定方針: 1項目でもFAILなら総合不合格（軽微なら「条件付き合格」とし条件を明記）。根拠のないPASSは禁止、必ず `docs/02-nfr.md` の該当箇所（見出し・行）を確認して判定する

| # | チェック項目 | 確認方法（根拠の探し方） |
|---|---|---|
| 1 | 全NFRが `## NFR-<番号>: <分類>` の見出し形式になっている。`分類` が `性能\|可用性\|セキュリティ\|コスト\|保守性\|互換性` のいずれか1つで表記ゆれがない。番号の重複・欠番がない | 各見出しを目視確認 |
| 2 | 全NFRに `要件` / `基準値` / `測定方法` / `関連US` の4項目がすべて記載されている | 各NFRエントリを1件ずつ確認 |
| 3 | `基準値`・`測定方法`に曖昧語（「適切に」「高速に」「使いやすく」等）が使われていない | `docs/02-nfr.md` 全体をgrep等で曖昧語検索 |
| 4 | `基準値`が数値・具体的な判定条件など測定可能な表現になっている（例: 秒数、件数、〇円、Yes/No判定可能な条件） | 基準値を1件ずつ確認し、数値または明確な条件が含まれるか確認 |
| 5 | 要件確認ノートに基づかない推測値（pm・builder-docsが新規に設定した基準値。特に性能NFR）には、推定である旨と前提条件（利用環境・想定データ規模等）が明記されている | 該当NFRの基準値の文中に「推定」等の明示と前提条件があるか確認 |
| 6 | 要件確認ノートの該当8項目（利用頻度、性能基準の扱い、復旧目標、運用費上限、機密情報の扱い、データ消失許容、想定件数、デバイス）が、すべて何らかのNFRに反映されている（作業指示書3節の対応表を用いて1項目ずつ突合） | 対応表の8項目を1つずつ`docs/02-nfr.md`内で検索し、反映箇所を特定できるか確認 |
| 7 | 各NFRの`関連US`に `docs/01-user-stories.md` に実在するUS-IDが記載されており、内容と矛盾しない（例: 性能NFRがUS-01/02/03/04のいずれかを指している等） | `関連US`欄のIDを`docs/01-user-stories.md`の見出しと突合 |
| 8 | Won't確定済みのUS-05〜US-11と矛盾するNFRが存在しない（新規バックアップ強化・スマホ対応・外部API連携前提の基準を要求していないか） | 各NFRの要件・基準値を、対応するWon'tストーリーの理由と突合 |
| 9 | ゲート4（設計）以降の実装詳細（具体的なDBインデックス設計・キャッシュ実装方式・ライブラリ選定等のHow）に踏み込みすぎていない。測定方法欄の具体的な計測手段の記述は許容する | 基準値・要件欄にHow相当の実装詳細が紛れ込んでいないか確認（測定方法欄は対象外） |
| 10 | 既存アプリのドメイン用語・アーキテクチャ制約（ローカルDocker運用、`Money`/`YearMonth`の制約、運用費0円）と矛盾する記述がない | `docs/basic_design.md`・プロジェクトCLAUDE.mdと記述を突合 |
| 11 | 末尾に「要件確認ノート項目との対応表」があり、要件確認ノートの8項目と反映先NFR-IDの対応が明示されている | 文書末尾の対応表を確認し、対応表とNFR本文の記載が一致するか突合 |

## 不合格時の差し戻し

- 差し戻し先: builder-docs
- 差し戻し方法: 上表でFAILとなった項目番号と、該当箇所（見出し・行）、修正すべき内容を明記して再依頼する
