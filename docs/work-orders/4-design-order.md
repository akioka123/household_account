## 3. 決定すべき設計論点（ここが本工程の核心。断定して書くこと）

### 3-1. 品目の小分類と既存 `LivingExpense.category` の関係

ゲート2で「既存category(5値固定: food/electricity/gas/mobile/communication)と新しい小分類(食品/生活用品等)は別概念であり断定しない」として先送りした論点。本工程で決定する。

**推奨方針**（この方向で設計し、根拠を文書に明記すること。別案が明らかに優れる場合のみ変更してよいが、その場合も理由を明記）:
- 小分類（食品/生活用品 等）は既存 `category` とは独立した、品目（レシート内の1行）に付与する新しい属性とする。既存の5値固定 `category` は変更しない
- レシート登録は既存の `LivingExpense`（`category="food"`）の下に、複数の品目（品目名・金額・小分類）をぶら下げる形にする。理由: レシートは主に食料品店での買い物であり、既存の「食費」区分の内訳を詳細化するものだから（`docs/00-requirements-notes.md` カテゴリ1参照）。「生活用品」小分類は既存の5値のどれにも該当しない支出だが、これは既存の枠組みを壊さず「食費レシートの中の内訳」として扱う
- 新しい子エンティティ名は `LivingExpenseItem`（またはより適切な名前があれば理由付きで提案）とし、`living_expense_id`（親への参照）・品目名・金額(`Money`)・小分類を持つ
- 小分類は当面 固定リスト（食品/生活用品、最低2種）とする。要件確認ノート・US-02が「複数の中から選べる最小条件」としているため、リストは列挙するが将来の追加を妨げない設計（DB上はVARCHAR等、Pythonのenum的定数リストは`living_expense.py`の`LIVING_EXPENSE_CATEGORIES`と同じパターンで別定数として定義）にする

### 3-2. レシート画像の保存

- ファイルシステム保存（`data/receipts/` 想定、要件確認ノート・企画書で確定済み）。DBには相対パスのみ保持
- 画像は `LivingExpense` に1件（1レシート=1画像、1:1）紐付ける想定で設計する。1つのLivingExpenseに複数画像を紐付ける要件はUS-01に見当たらないため、over-engineeringしない

### 3-3. 貼り付け一括登録（US-03、Should）の入力形式

- 具体的なテキスト/JSON形式を1つ決定して明記すること（例: 1行1品目、タブ区切りで「品目名\t金額\t小分類」、または `[{"name":..,"amount":..,"category":..}]` のJSON配列）。形式は貼り付け元がClaudeとの対話で得たテキストであることを踏まえ、人間が目視で確認・修正しやすい形式を推奨する
- 保存前にプレビュー編集ができること（US-03受け入れ基準）を画面設計に反映する
- 想定外形式のエラー表示（US-03受け入れ基準）をモジュール設計（バリデーション）に反映する

## 4. 画面設計への反映

- 既存の月次画面（`docs/basic_design.md` 2.3節、`/month/{year}/{month}`）の生活費セクションに、レシート登録の入力（画像アップロード・貼り付け登録・品目一覧編集）と、小分類別集計表示（品目名は表示しない）を追加する形で設計する。新規の別画面を起こす必然性がなければ既存画面の拡張として設計し、過剰な画面追加をしない
- 既存の生活費簡易入力（品目内訳なし）は残し、両方式が共存する（US-05, Won't確定済み）ことが画面上どう表現されるかを明記する

## 5. DB設計・マイグレーション

- 新テーブル（例: `living_expense_item`）のカラム設計、外部キー制約、既存`living_expense`テーブルへのカラム追加（画像パス）を設計する
- マイグレーションファイル名は `alembic/versions/<3桁連番>_<説明>.py` の連番規則に従う想定である旨を明記する（実際のファイル作成はゲート5=実装工程で行う。本工程では設計のみ）
- NFR-08（保守性、想定件数100件/月20〜30件）を前提にした設計であることを明記し、過剰なインデックス設計等をしない

## 6. スコープ・記述レベルの注意

- 4層アーキテクチャ（presentation → application → domain、infrastructure → application/domain）の依存方向を守った設計にする
- Port命名規則（`SqlAlchemy<名前>Repository`）・DI規約（`provide_<名前>`関数 + `Annotated[..., Depends(...)]`）に従う
- US-05〜US-11（Won't確定済み）と矛盾する設計をしない（外部API呼び出し設計、スマホ対応レイアウト、自動バックアップ機構などを設計に含めない）
- NFR-01〜09の基準値（画像アップロード5秒以内、htmx部分更新200ms等）を満たせる設計であることを、該当モジュール設計の箇所で言及する
