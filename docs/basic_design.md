## household_account 基本設計書

### 1. 前提・システム構成

- **目的**: 引っ越し後の家計を年月単位で記録し、月次損益と年次推移を可視化するローカルアプリを提供する。
- **技術スタック**
  - バックエンド: Python / FastAPI
  - フロントエンド: HTML テンプレート + htmx
  - データベース: PostgreSQL（Docker コンテナ上で動作）
- **利用形態**
  - ローカル環境（localhost）で単一ユーザが利用
  - 認証機能なし

---

### 2. 画面構成設計

#### 2.1 共通レイアウト

- **共通ヘッダ**
  - アプリタイトル: 「家計簿ダッシュボード」
  - 年選択ドロップダウン:
    - 現在年をデフォルトとし、「一定範囲の年（例: 現在年±5年）」を選択可能とする
    - その中で、既にデータ登録のある年はマーク（例: アイコンや強調表示）して区別する
  - グローバルナビゲーション
    - 「年次ダッシュボード」リンク: `/dashboard/{year}`
    - 「設定」リンク: `/settings`
- **共通フッタ**
  - バージョン情報、簡易ヘルプリンク
- **メインコンテンツ**
  - 画面ごとにメインコンテンツ領域を持ち、htmx による部分更新対象とする。

#### 2.2 年次ダッシュボード画面 `/dashboard/{year}`

- **目的**
  - 指定年における月次損益・収支内訳の推移と、年収推移を俯瞰する。

- **レイアウト**
  - 上部: 年度切替（ドロップダウン）、「前の年」「次の年」ボタン
  - 中央:
    - グラフ領域（縦に 2 つ）
      - グラフ1: 月次推移グラフ
        - 横軸: 年月（1〜12 月）
        - 縦軸: 金額
        - 系列: 手取り収入 / 固定費 / 変動費 / 損益
      - グラフ2: 年収推移
        - 横軸: 年
        - 縦軸: 年収（額面、手取り）
        - 系列: 年収（額面） / 年収（手取り）
  - 下部: 月別サマリ一覧
    - 見出し行: 「変動費の月平均」表示、「すべての内訳を表示」ボタン
    - 集計行: 年間の合計（表示中の内訳列にも合計を出す）
    - 各行: `年月`, `手取り収入`, `固定費`, `変動費`, `生活費`, `損益`, `メモ`, 「詳細」ボタン

- **主な表示項目**
  - 年選択: `year`（整数）
  - 月別一覧（12 行想定）
    - 年月: `year_month`（YYYY-MM）
    - 手取り収入合計（`salary_net + bonus_net`）
    - 固定費合計（`fixed_total(ym)`）
    - 変動費合計（`variable_total(ym)`）＋ 平均比（`variable_total(ym) - 変動費の月平均`）
    - 生活費合計（カテゴリ別生活費の合計）
    - 損益（`profit(ym)`）
    - メモ（月次メモ `month_notes.note`。未入力時は `—`、長文は省略表示し `title` 属性で全文）
  - 変動費の月平均: サマリのある月のみを対象とした `variable_total` の平均（小数切り捨て）

- **内訳エクスパンド（列の開閉）**
  - 行を展開するのではなく、**列を増減させる**方式とする。
    見出しのトグルを押すと、その内訳列が全行（集計行を含む）に対してまとめて表示・非表示される。
  - `変動費` 見出しのトグル → 内訳列を 2 列追加
    - 現金: `cash_spent(ym)`
    - カード変動費: `variable_card(ym)`（＝ カード請求総額 - カードに含まれる固定費）
      - カード請求総額そのものではない点に注意。内訳の合計が `variable_total(ym)` に一致するよう、
        固定費分を除いた金額を表示する。
  - `生活費` 見出しのトグル → 内訳列を 5 列追加
    - 食費 / 電気代 / ガス代 / 携帯料金 / 通信費
  - 2 つのグループは独立して開閉できる。「すべての内訳を表示」ボタンで一括開閉する。
  - 内訳列は初期状態で非表示（`hidden`）とし、HTML には常に出力しておく。
    開閉は静的 JS（`/static/js/dashboard-expand.js`）が `hidden` を付け外しするだけで、サーバ通信を伴わない。
    htmx による差し替え後も動作するようイベント委譲で実装する。
  - 内訳列は視認性のため背景色を付ける（変動費: 青系、生活費: 緑系）。
    列数が増えるため、表は横スクロール可能なコンテナに入れる。

- **入力・操作**
  - 年選択ドロップダウン変更
    - htmx による GET `/dashboard/{year}` 再読み込み
  - 「詳細」ボタン（各月行）
    - 遷移: `/month/{year}/{month}`
  - 「年次全体を CSV 出力」ボタン
    - GET `/dashboard/{year}/export.csv` を呼び出し、当年の全体を CSV ダウンロードする。

- **CSV 出力（`/dashboard/{year}/export.csv`）**
  - 文字コード: UTF-8（BOM 付き。Excel での文字化けを防ぐため）
  - ファイル名: `dashboard_{year}.csv`
  - 列: `年月`, `手取り収入`, `固定費`, `変動費`, `現金支出`, `カード変動費`, `生活費合計`,
    `食費`, `電気代`, `ガス代`, `携帯料金`, `通信費`, `損益`, `変動費平均差`, `メモ`
  - 行: 月次行（サマリのある月）→ `集計` 行 → `平均` 行（小数切り捨て）

- **htmx 部分更新**
  - 年選択変更時に、以下の領域を部分更新対象とする。
    - 月次推移グラフ
    - 年収推移グラフ
    - 月別サマリ一覧
  - ルートハンドラ側で、`year` パラメータに応じた HTML 部分テンプレートを返す。

#### 2.3 月次画面 `/month/{year}/{month}`

- **目的**
  - 指定年月の家計情報（収入・固定費・変動費・現金）を入力・閲覧し、月次損益を確認する。

- **レイアウト**
  - 上部: 対象年月表示・年月切替（前月 / 次月）
  - その下にタブナビゲーション（htmx によるタブコンテンツ切替）
    - 「集計」タブ
    - 「変動費」タブ
    - 「現金」タブ
    - 「固定費」タブ
    - 「収入」タブ

- **共通タブエリア**
  - タブヘッダ: 各タブのボタン
    - クリック時に htmx による部分 GET（例: `/month/{year}/{month}/tab/summary`）を実行
    - コンテンツ表示領域のみ更新

##### 2.3.1 集計タブ

- **目的**
  - 当月の損益サマリと、入力不足に関する警告の表示。

- **表示項目**
  - 当月サマリ
    - 手取り収入合計: `salary_net + bonus_net`
    - 固定費合計: `fixed_total(ym)`
    - カード変動費合計: `variable_card(ym)`
    - 現金支出: `cash_spent(ym)`
    - 変動費合計: `variable_total(ym)`
    - 損益: `profit(ym)`
  - 警告メッセージ
    - 次月月初現金未入力
    - カード変動費が負値になっているカード
  - 消費理由メモ（当月の消費が平均以上／平均以下になった理由）

- **入力**
  - 消費理由メモ: `note`（テキストエリア、500 文字以内、任意）
    - POST `/month/{year}/{month}/note` で保存し、集計タブを再描画する。
    - 空欄で保存した場合はメモを削除する。
    - 500 文字超過時はエラーメッセージを表示し、保存しない。
    - 保存したメモは年次ダッシュボードの変動費エクスパンド内に表示される。
  - 上記以外の金額は集計タブに入力フォームを持たず、他タブでの入力内容を反映した結果を表示する。

- **htmx 部分更新**
  - 他タブでデータ登録後、サマリ領域のみ再取得する API を呼び出す。
    - 例: POST 後に `hx-get="/month/{year}/{month}/tab/summary"` で差分更新。
  - 消費理由メモの保存は `hx-post` でタブコンテンツ領域のみ更新する。

##### 2.3.2 変動費タブ（カード請求）

- **目的**
  - カード別の当月請求総額を登録・更新する。

- **表示・入力項目**
  - 繰り返し行（行数は設定で上限管理、初期最大 20 件）
    - カード名（プルダウン）: `card_id`
    - 請求総額（数値）: `amount`（>= 0）
  - 行追加ボタン（上限まで）
  - 行削除ボタン（不要行を削除）

- **バリデーション**
  - 金額は 0 以上の整数（または小数点 2 桁まで）
  - カードは有効なカードマスタに存在すること

- **htmx 部分更新**
  - 行追加・削除時にタブコンテンツ領域のみ更新
  - 保存ボタン押下時に、POST `/month/{year}/{month}/card-statements` を呼び出し、結果に応じて
    - エラー時: 入力フォーム＋エラーメッセージ部分更新
    - 正常時: 変動費タブの再描画＋集計タブのサマリ領域を別途再取得

##### 2.3.3 現金タブ

- **目的**
  - 月初現金、当月引出、次月月初現金を登録し、現金支出の差分計算を可能にする。

- **表示・入力項目**
  - 月初現金: `cash_start(ym)`（数値、必須）
  - 引出明細（複数行）
    - 日付: `withdrawal_date`
    - 金額: `amount`
    - メモ: `note`（任意）
  - 次月月初現金: `cash_start(next_ym)`（数値、任意だが未登録時は警告対象）

- **バリデーション**
  - 金額は 0 以上
  - 日付は対象月内の日付

- **htmx 部分更新**
  - 引出行の追加・削除はタブ内のみ更新
  - 保存時に POST `/month/{year}/{month}/cash` を呼び出し、結果に応じて現金タブ＋集計タブサマリを再取得。

##### 2.3.4 固定費タブ

- **目的**
  - 固定費マスタの履歴管理（適用開始月と金額、カード紐づけ）を行う。

- **表示・入力項目（当月時点で有効な固定費の一覧）**
  - 項目名: `name`
  - 適用開始年月: `effective_from_ym`
  - 金額: `amount`
  - カード紐づけ: `card_id`（任意）
  - カード含有フラグ（カード請求に含まれる固定費かどうか）: `included_in_card`（bool）

- **操作**
  - 追加: 新規固定費の履歴行を追加（`effective_from_ym` >= 当月）
  - 変更: 金額や紐づけカード、フラグを変更する際は、新規履歴（当月または将来月）を追加
  - 削除: 金額 0 の履歴を追加（終了日は持たない）

- **htmx 部分更新**
  - 行追加・編集フォームをモーダルまたは行内編集で実装し、その部分のみ更新
  - 登録完了後、固定費タブコンテンツ＋集計タブサマリを再取得

##### 2.3.5 収入タブ

- **目的**
  - 当月の月例給与・賞与の額面/手取りを登録する。

- **表示・入力項目**
  - 月例給与
    - 額面: `salary_gross`
    - 手取り: `salary_net`
  - 賞与
    - 額面: `bonus_gross`
    - 手取り: `bonus_net`

- **バリデーション**
  - 各金額は 0 以上

- **htmx 部分更新**
  - 保存時に POST `/month/{year}/{month}/income`、結果に応じて収入タブ＋集計タブサマリを再取得。

#### 2.4 設定画面 `/settings`

- **目的**
  - カードマスタおよび各種上限件数を管理する。

- **レイアウト**
  - 上部タブ
    - 「カード管理」タブ
    - 「上限設定」タブ

##### 2.4.1 カード管理タブ

- **表示・入力項目**
  - カード一覧
    - カード名: `card_name`
    - ステータス: `enabled`（有効/無効）
  - 追加フォーム
    - カード名入力欄

- **操作**
  - 追加: 新規カードを登録
  - 名称変更: 既存カードの名称編集
  - 無効化: `enabled` フラグを false にする（過去データは残す）

- **htmx 部分更新**
  - 追加・更新・無効化操作時に、カード一覧部分のみ更新。

##### 2.4.2 上限設定タブ

- **表示・入力項目**
  - 変動費最大件数: `max_variable_items`（初期値 20）
  - 固定費最大件数: `max_fixed_items`（初期値 20）

- **操作**
  - 入力値更新後、保存ボタンで POST `/settings/limits` を呼び出し、正常時は更新済み値を反映して再表示。

#### 2.5 固定費一覧画面 `/fixed-items`

固定費の棚卸し（見直し候補の特定）を目的とした、月をまたいだ俯瞰用の独立画面。ヘッダーのグローバルナビゲーションから遷移する。データの登録・変更は行わず、参照専用。

- **パラメータ**
  - `ym`（クエリ、`YYYY-MM` 形式、省略可）: 基準年月。省略時は当月。
  - 不正な形式・範囲外の値は 400 を返さず、**当月にフォールバックして表示する**（本アプリはエラー画面を持たないため）。

- **表示項目**
  - サマリ: 月額合計 / 年額換算合計（月額合計 × 12）/ 有効項目数
  - 有効な固定費テーブル（**月額の降順**、同額は項目名の昇順）
    - 項目名 / 月額 / 年額換算 / 割合 / カード / カード請求 / 適用開始 / 経過月数
    - 割合 = 月額 ÷ 月額合計 × 100（月額合計が 0 の場合は `-`）
    - 経過月数 = 基準年月 − 現在額の適用開始年月（月数）
    - 合計行に月額合計・年額換算合計を表示
  - 改定履歴（行の展開で表示）: 適用開始 / 金額 / 前回差分 / カード
    - 前回差分は初回が `—`、増額を赤・減額を緑で表示。運用終了（金額 0）の行は金額欄に「運用終了」と表示し差分は出さない
    - 履歴は基準年月で絞り込まず**全期間**を表示する（現在額の判定にのみ基準年月を使う）
  - 運用終了済みセクション（終了年月の降順）: 項目名 / 終了年月 / 経過月数
    - 運用終了項目は月額合計・年額換算合計・有効項目数に**含めない**
  - 固定費が 0 件の場合は、月次画面の固定費タブへの導線を表示

- **算出**
  - 基準年月時点で有効な履歴（`effective_from <= 基準年月`）を対象に、`FixedExpenses.get_effective_histories()` で項目ごとの最新履歴を確定する。月次画面・ダッシュボードと同一の集約を再利用するため、固定費合計の定義は全画面で一致する。
  - リポジトリへの問い合わせは `find_all()` の 3 回（固定費項目・固定費履歴・カード）のみとし、絞り込みと集計はメモリ上で行う。

- **htmx 部分更新**
  - 基準年月セレクタの変更時に `#fixed-items-content` のみ更新（`HX-Request` ヘッダがある場合は本体部分のみを返す）。
  - 改定履歴の開閉はサーバ往復なしのクライアントサイド処理（`static/js/fixed-items-expand.js`）。

- **前提**
  - 同一の固定費項目・同一の適用開始年月の履歴は 1 行に限られる（`UNIQUE(fixed_item_id, effective_from)`、マイグレーション 009）。このため `get_effective_histories()` の厳密比較（`>`）で同着が起きることはない。同月内に金額を入れ直した場合は追加ではなく上書きになる。詳細は「7. 固定費履歴の一意性」を参照。

#### 2.6 総合ダッシュボード画面 `/dashboard/overall`

複数年にまたがる年収・月次推移を俯瞰する画面。ヘッダーのグローバルナビゲーションから遷移する。データの登録・変更は行わず、参照専用。

- **パラメータ**
  - なし（表示期間は「当年の5年前 〜 当年」に固定）

- **表示項目**
  - 年収推移グラフ: 横軸=年、系列=年収（額面）/ 年収（手取り）
  - 選択項目推移グラフ: 横軸=年月、系列はセレクタで切替（損益 / 手取り / 変動費）

- **算出**
  - `GetOverallDashboardDataUseCase.execute(start_year, end_year)` が、`MonthSummaryRepository.find_by_years()` で期間内の月次サマリを、`IncomeRepository.find_by_years()` で期間内の収入をそれぞれ取得し、年ごとの額面・手取り合計に集約する
  - 月次サマリの計算式は 2.2 の年次ダッシュボードと同一（`GetMonthSummaryUseCase` に一本化）

- **htmx 部分更新**
  - なし（グラフはページ読み込み時に埋め込みJSONから描画。`static/js/overall-dashboard-chart.js` + Chart.js）

### 3. ログ設計

#### 3.1 ログ種別

- **アクセスログ**
  - 対象: 全 HTTP リクエスト
  - 項目: タイムスタンプ, メソッド, パス, ステータスコード, 所要時間, クライアント IP
- **アプリケーションログ（ビジネスイベント）**
  - 月次データ登録、固定費履歴更新、収入登録などの主要イベント
- **エラーログ**
  - 予期しない例外、検証エラーの詳細、外部要因による失敗
- **DB 例外ログ**
  - PostgreSQL 接続エラー、タイムアウト、クエリ失敗など

#### 3.2 出力先

- **標準出力**
  - Docker コンテナ運用を前提に、アクセスログおよびアプリケーションログを標準出力に出力
- **ローテーションファイル（任意）**
  - ローカルデバッグ用途で、アプリケーションログをファイル出力するオプションを用意

#### 3.3 ログフォーマット

- 共通項目
  - `timestamp`（ISO8601）
  - `level`（DEBUG/INFO/WARNING/ERROR）
  - `logger`（モジュール名）
  - `request_id`（リクエスト単位のトレース ID）
  - `screen`（画面識別子: dashboard, month, settings 等）
  - `context`（`year`, `month`, `card_id` などのコンテキスト情報）

#### 3.4 ログ出力ポイント

- **画面表示**
  - `/dashboard/{year}` へのアクセス: INFO レベルで年を記録
  - `/month/{year}/{month}` 初期表示: 対象年月を INFO ログ
- **登録・更新イベント**
  - カード請求登録、現金情報登録、固定費履歴登録、収入登録の成功/失敗
- **集計処理**
  - 月次サマリ算出時に、算出対象の年月と処理時間を DEBUG/INFO レベルで出力
- **警告検出処理**
  - 次月月初現金未入力、カード変動費負値発生時に WARNING ログを出力
- **DB 例外**
  - PostgreSQL 接続エラー、トランザクション失敗などを ERROR レベルで記録

#### 3.5 ログレベル運用

- DEBUG: 開発時の詳細なトレースに使用（本番想定ではオフまたは限定）
- INFO: 通常の操作・処理完了を記録
- WARNING: 入力不足や整合性チェックの警告
- ERROR: 例外や処理失敗（ユーザ操作では回復不能なもの）

### 4. パフォーマンス要件

#### 4.1 レスポンスタイム目標

- 年次ダッシュボード初期表示: 平均 300ms 以内（ローカル環境）
- 月次画面初期表示: 平均 300ms 以内
- タブ切替（htmx 部分更新）: 平均 200ms 以内

#### 4.2 同時実行数想定

- 単一ユーザ利用を前提とし、FastAPI 実行サーバ（uvicorn）は 1〜2 ワーカーで十分。
- ブロッキング I/O を避けるため、DB アクセスは非同期ドライバ（例: asyncpg）＋SQLAlchemy を想定。

#### 4.3 DB 設計ガイドライン（PostgreSQL）

- 主キー: 各エンティティに整数または UUID の主キーを付与
- インデックス
  - `YearMonth` エンティティ: `year_month` にインデックス
  - `CardStatement`: `(year_month, card_id)` の複合インデックス
  - `Withdrawal`: `year_month` + 日付
  - `FixedItemHistory`: `effective_from_ym`, `card_id`
  - `MonthNote`（`month_notes`）: `year_month` に一意インデックス（1 年月につき 1 件）
- トランザクション
  - 各登録イベントは 1 トランザクションで完結させる。
  - 集計処理は基本的に参照のみとし、必要に応じて読み取り一貫性レベルを選択。

#### 4.4 データ量前提

- 想定利用期間: 10 年程度
- 月数: 最大 120 ヶ月分
- カード枚数: 10 枚程度
- 各月の引出・固定費・カード請求件数: 上限 50〜100 件規模
- この規模では PostgreSQL 単一インスタンスで十分性能を満たす想定。

### 5. イベント駆動の処理設計

#### 5.1 主なイベント一覧

- 年次ダッシュボード表示
  - イベント: `/dashboard/{year}` へのアクセス
- 月次画面表示
  - イベント: `/month/{year}/{month}` へのアクセス
- タブ切替
  - イベント: `/month/{year}/{month}/tab/{tab_name}` への htmx リクエスト
- 年次全体の CSV 出力
  - イベント: GET `/dashboard/{year}/export.csv`
- 消費理由メモ登録
  - イベント: POST `/month/{year}/{month}/note`
- カード請求登録
  - イベント: POST `/month/{year}/{month}/card-statements`
- 現金情報登録
  - イベント: POST `/month/{year}/{month}/cash`
- 固定費履歴登録
  - イベント: POST `/month/{year}/{month}/fixed-items`
- 収入登録
  - イベント: POST `/month/{year}/{month}/income`
- 設定変更（カード管理、上限設定）
  - イベント: POST `/settings/cards`, `/settings/limits`

#### 5.2 処理フロー（例: カード請求登録）

1. 入力値受信（カード ID, 金額リスト）
2. バリデーション
   - カード ID が有効か
   - 金額が 0 以上か
3. トランザクション開始
4. 既存の当月 `CardStatement` を削除または更新
5. 新しい `CardStatement` レコードを一括登録
6. トランザクションコミット
7. 集計ロジック呼び出し
   - `variable_card(ym) = Σ card_statement(ym, card) - Σ fixed_in_card(ym, card)`
   - `variable_total(ym) = variable_card(ym) + cash_spent(ym)`
   - `profit(ym)` を算出
8. 警告判定
   - カード変動費が負値となるカードがあるか
9. htmx 用レスポンス生成
   - 変動費タブ HTML
   - 必要に応じて集計タブサマリ部分も更新

#### 5.3 処理フロー（例: 現金情報登録）

1. 月初現金・引出明細・次月月初現金を受信
2. バリデーション
3. トランザクション開始
4. `CashBalance`、`Withdrawal` エンティティを更新
5. トランザクションコミット
6. `cash_spent(ym)` を計算
   - `cash_spent(ym) = cash_start(ym) + sum(withdrawals(ym)) - cash_start(next_ym)`
7. `variable_total(ym)` および `profit(ym)` を再計算
8. 次月月初現金未入力の場合、警告フラグを立てる
9. 現金タブおよび集計タブサマリを部分更新

#### 5.4 処理フロー（例: 固定費履歴登録）

1. 固定費名、適用開始年月、金額、カード紐づけ、カード含有フラグを受信
2. バリデーション（適用開始年月の形式、金額 >= 0 など）
3. トランザクション開始
4. `FixedItemHistory` に新規履歴を追加
5. トランザクションコミット
6. 当月の `fixed_total(ym)` を算出
   - `fixed_total(ym) = Σ fixed_amount where effective_from <= ym`
7. 当月の `variable_card(ym)`、`variable_total(ym)`、`profit(ym)` を再計算
8. カード変動費が負値の場合は警告
9. 固定費タブおよび集計タブサマリを部分更新

#### 5.5 処理フロー（例: 収入登録）

1. `salary_gross`, `salary_net`, `bonus_gross`, `bonus_net` を受信
2. バリデーション
3. トランザクション開始
4. `Income` エンティティを当月分で更新
5. トランザクションコミット
6. `profit(ym)` を再計算
7. 年次ダッシュボード用の `annual_gross`, `annual_net` を再集計
8. 収入タブおよび集計タブサマリを部分更新

### 6. Docker を用いた環境構成（PostgreSQL）

#### 6.1 コンテナ構成

- `app` コンテナ
  - 役割: FastAPI アプリケーションの実行
  - ベースイメージ: `python:3.12-slim`（例）
  - 起動コマンド: `uvicorn app.main:app --host 0.0.0.0 --port 8000`
- `db` コンテナ
  - 役割: PostgreSQL サーバ
  - ベースイメージ: `postgres:16`
  - ポート: 5432
  - 永続化: 名前付きボリュームを `/var/lib/postgresql/data` にマウント

#### 6.2 docker-compose 構成方針

- サービス定義（概略）
  - `app`
    - `build`: アプリケーション用 Dockerfile
    - `environment`:
      - `DB_HOST=db`
      - `DB_PORT=5432`
      - `DB_USER=household`
      - `DB_PASSWORD=secret`（実際は `.env` で管理）
      - `DB_NAME=household`
    - `depends_on`: `db`
    - `ports`: `8000:8000`
  - `db`
    - `image`: `postgres:16`
    - `environment`:
      - `POSTGRES_USER=household`
      - `POSTGRES_PASSWORD=secret`
      - `POSTGRES_DB=household`
    - `volumes`:
      - `db-data:/var/lib/postgresql/data`

- ボリューム
  - `db-data`: PostgreSQL データファイル永続化用

#### 6.3 環境変数・設定

- DB 接続文字列は環境変数から組み立てる。
  - 例: `postgresql+asyncpg://{DB_USER}:{DB_PASSWORD}@{DB_HOST}:{DB_PORT}/{DB_NAME}`
- アプリ設定
  - ログレベル
  - ポート番号（8000）

#### 6.4 バックアップ/エクスポート

- `pg_dump` を用いて SQL またはカスタム形式でエクスポートする。
- Docker 環境では、`db` コンテナに対して `pg_dump` を実行し、ホスト側にバックアップファイルを出力できるようにする方針とする。

### 7. 固定費履歴の一意性

#### 7.1 方針

`fixed_item_histories` は「その固定費項目が、その年月から いくら になるか」を表す。同一の `(fixed_item_id, effective_from)` に対して金額は 1 つに定まるため、**`UNIQUE(fixed_item_id, effective_from)` を課す**（マイグレーション 009）。

これは本スキーマの既存規約に揃えたものである。

| 分類 | テーブル | 制約 |
|---|---|---|
| 月の状態（その月の値は 1 つ） | `incomes` | `UNIQUE(year_month)` |
| | `card_statements` | `UNIQUE(year_month, card_id)` |
| | `cash_balances` | `UNIQUE(year_month)` |
| | `month_notes` | `UNIQUE(year_month)` |
| | `fixed_item_histories` | `UNIQUE(fixed_item_id, effective_from)` |
| 月の明細（複数行が正しい） | `withdrawals` | なし |
| | `living_expenses` | なし |

#### 7.2 同月内の訂正

同じ適用開始年月で登録し直した場合は、履歴を追加せず**既存行を上書きする**（`FixedItemHistoryRepository.save` の契約）。収入・カード請求・現金と同じ振る舞いになる。

- 「2026-05 から 60,000 円」を登録したあと「2026-05 から 60,440 円」を登録 → 1 行（60,440 円）
- 「2026-05 から運用終了」のあと同じ年月に金額を登録 → 終了が取り消され、その金額が有効になる
- 「2026-05 から 60,440 円」のあと同じ年月に運用終了 → 運用終了になる
- 適用開始年月が異なる場合は上書きせず、改定履歴として別行で残る

訂正そのものの履歴（いつ訂正したか）は保持しない。改定履歴画面は「1 年月 = 1 金額」で表示される。

#### 7.3 年月粒度である理由

`effective_from` を日付ではなく年月 (`YYYY-MM`) にしているのは、本アプリの集計単位が月だからである。日付にすると「月内に金額が変わった月の金額」を決めるルール（月内の最後を採るのか、1 日時点か、日割りか）が別途必要になるが、`MonthCalculator` に日割りの定義は無く、要件上も固定費に終了日は持たせない方針である。日付は「いつ変更を記録したか」を表す別の関心事であり、`effective_from` の型とは分けて考える。
