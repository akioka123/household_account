# docs/incidents/ 運用規約(障害対応ADR)

household_account プロジェクトで発生した不具合(バグ)の調査・原因・修正方針を記録するディレクトリ。
`docs/decisions/` が設計判断の記録であるのに対し、こちらは「発生した障害への対応」の記録に特化する。

## 対象

- ユーザー操作で発生した不具合(データ破損・誤動作・例外)で、原因調査と修正方針の決定を要するもの
- 軽微な文言修正・スタイル調整など hotfix-flow の `docs/maintenance/MN-*.md` で足りるものは対象外(この
  ディレクトリは「原因の分析」と「再発防止のための決定」を要する障害に限定し、記録の重複を避ける)

## ファイル名

`ADR-<3桁連番>-<内容を表す短い英語スラッグ>.md`(例: `ADR-001-living-expense-item-id-collision.md`)。
連番はゼロ埋め3桁で採番し、既存ファイルの最大連番+1を使う。`docs/decisions/` とは別の連番系列。

## フロントマター(必須)

**あとから機械的に参照・一覧できるよう、本文の前に必ず YAML フロントマターを付ける。** フロントマターのない
ADRを新規作成しない。`docs/decisions/CLAUDE.md` と同じスキーマを使う。

```yaml
---
id: ADR-001
title: 短いタイトル(本文見出しと同じ内容)
status: 検討中 | 承認済 | 却下 | 廃止
date: 2026-08-27
supersedes: null      # このADRが置き換える既存ADRのid(なければnull)
superseded_by: null   # このADRを置き換えた後続ADRのid(未使用ならnull。廃止時に埋める)
tags: [任意のキーワード]
---
```

- `status` が変わったとき(検討中→承認済 等)は本文の「日付: / 状態:」行と両方を更新する
- 既存ADRを別のADRが置き換える場合、古い方の `status: 廃止` と `superseded_by`、新しい方の `supersedes` を両方更新する

## 本文構成

`docs/decisions/` と同様、以下の見出しをこの順で書く(該当がなければ「なし」と明記し、見出し自体は省略しない):

1. `## 背景(Why)` — 症状・再現手順・影響範囲
2. `## 原因` — コード上の根本原因(ファイル・行を明記)
3. `## 決定(What)` — 採用する修正方針
4. `## 実施方法(How)` — 具体的な変更箇所・検証方法(テスト実行結果を含む)
5. `## 採らなかった選択肢と理由(Why not)`
6. `## しないこと(スコープ除外)`
7. `## 再検討条件`

「背景」「原因」の2本立てにしている点が `docs/decisions/` との違い(設計判断のADRには原因分析が不要なため)。

## 修正着手前の運用

hotfix-flow でバグ修正に着手する際、原因調査で設計判断・トレードオフを伴う場合(例: 採番方式の変更、
スキーマ変更を要する修正など)は、着手前に本ディレクトリへADRを作成してからコードを修正する。
単純な typo 修正など決定を伴わない修正は対象外(hotfix-flow の MN ファイルのみでよい)。
